# Contributing to Vise

Thanks for helping improve Vise. This document is the enforceable version of
the project's expectations: what a pull request must do, what it must not
break, and how it is reviewed. It is intentionally short — the architecture
itself lives in [docs/DESIGN.md](docs/DESIGN.md), and the test points a PR is
expected to cover live in [docs/TEST-PLAN.md](docs/TEST-PLAN.md).

Vise is a **local resource-management layer**. Every tool or knowledge base is
onboarded once as an *adapter* behind a single machine-readable entry point
(`visectl` / `viseinit`). The rules below exist to keep that single entry
point trustworthy.

If you are only reading the code to understand it, start with
[README.md](README.md) and [AGENTS.md](AGENTS.md) instead.

---

## 1. Where your change belongs

Vise is four layers. Putting a change in the wrong layer is the most common
review finding, so locate yours first:

| Layer | Owns | Files |
| --- | --- | --- |
| L1 Setup | install, uninstall, and the uninstall ledger | `init/setup.sh`, `init/uninstall.sh`, `init/register_adapters.py`, `init/pick_pip_index.py`, `core/manifest.py` |
| L2 Shared config | path resolution, portable config | `core/adapter_paths.json`, `core/vise_adapter_paths.py`, `.vise/tool_paths.json` (generated) |
| L3 Adapter | per-resource contract and implementation | `adapters/<Name>/vise.adapter.json`, `thread`, `src/`, `README.md` |
| L4 Entry | the single user/agent surface, incl. shell integration | `core/visectl.py`, `core/viseinit.py`, `core/vise_mcp.py`, `core/vise_functions.sh` |

Rules of placement:

- A **new resource** is an adapter (L3) — never a new top-level script or a
  new shell function. Adapters are reached *only* through `visectl`.
- **Path/portability** concerns belong in L2, not baked into adapters.
- Anything an agent calls belongs in L4 with `--json` and stable exit codes.

## 2. Non-negotiable contracts

These are invariants, not preferences. A PR that breaks one is not merged
without a prior design discussion (open an issue / draft PR first).

| # | Contract | Why it exists |
| --- | --- | --- |
| C1 | **One entry point.** Adapters are invoked only via `visectl run` / `viseinit`. No adapter ships a globally-installed command as its primary interface. | Function-name collisions and unreviewable side effects are what Vise replaces. |
| C2 | **The manifest is the single source of truth.** An adapter's `vise.adapter.json` fully describes it; the registry is a *generated projection*. | Contributors must never hand-edit `registry.json`; the registry is machine-local. |
| C3 | **Stable exit codes (`0`–`6`).** `0` all OK, `1` generic failure, `2` missing dependency, `3` init step failed, `4` healthcheck failed, `5` unknown adapter, `6` manifest error. | Agents branch on these; changing them silently breaks consumers. |
| C4 | **`--json` on every command.** Machine-readable output is a first-class interface, not an afterthought. | Agents consume JSON, not human tables. |
| C5 | **`visectl run` uses the adapter directory as its cwd.** Files outside it must be addressed with absolute paths, and docs must say so. | Predictable, reproducible invocation. |
| C6 | **`init_steps` use the structured form** (`run` + `args`). The legacy `command` string is an escape hatch and needs justification. | No shell-quoting fragility; no surprise interpretation. |
| C7 | **Generated artifacts are never committed.** `.vise/` (`tool_paths.json`, `registry.json`, `requirements.txt`, `python`, `state/`, `reports/`, `installed.json`, `baseline/`, `snapshots/`, `patches/`) and `.venv/` are all gitignored. | They are machine-local and go stale; committing them causes conflicts. |
| C8 | **No implicit or silent execution.** Vise must not run code without an explicit user/agent action — no `PROMPT_COMMAND` hooks, no always-on watchers. Any shell reload is *trigger-based* (performed in response to a `vise*` command). | Silent execution is both a security risk and impossible to audit. |
| C9 | **Outside-`VISE_ROOT` writes are recorded in the uninstall ledger.** Any installer or `thread` that writes outside the repo (e.g. `~/.local/bin` wrappers, rc blocks) must call `core/manifest.py add ...`; wrapper files must keep the `# Auto-generated by <source> - do not edit.` header. | Uninstall must be able to remove exactly what Vise added; the header is the fallback-scan marker. |
| C10 | **Idempotency.** `setup.sh`, every `thread`, and rc injection must be safe to run repeatedly with no duplicated or contradictory effects. | Re-running setup is routine (new tool, new adapter). |
| C11 | **Cross-platform shell.** Target **Linux + Git Bash on Windows**, bash only (zsh tolerated for rc detection). Edit files with Python, not `sed -i`; no PowerShell. | `sed -i` and PowerShell are the two recurring portability failures. |
| C12 | **Path changes are a repo-wide edit.** Renaming or moving a core entry file requires updating every hardcoded reference: `init/setup.sh`'s injected template, all docs, and the rc files already injected on user machines. | A missed reference fails silently. |
| C13 | **Adapter-code changes go through the guard.** Before editing an adapter's source, take a snapshot (`visectl adapter snapshot <id> -m "why"`); validate with `viseinit <id>`; then either restore (`visectl adapter restore <id>`) or promote (`visectl adapter promote <id> -m "why"`). `promote` **writes a patch and never commits** — committing stays a deliberate act. A modified adapter with no open snapshot is *unprotected*: `visectl run` and `promote` refuse it with exit `7`. | An agent that "mostly" solves a task with an existing tool will edit it; without a snapshot the original is unrecoverable, and without a patch the improvement is lost. This must work for a zip/tarball install too, so it never depends on git. |

Safety and destructive operations additionally follow the house style:

- Destructive/irreversible actions ship with a `--dry-run` (or `preview`)
  equivalent (`viseinit --dry-run`, `uninstall.sh --dry-run`, `file_patch
  preview`, `visectl adapter restore --dry-run`).
- Tool-version requirements are declared (`required_cots` with
  `min_version`), not assumed.
- Exit-code `7` belongs to the **guard domain** (C13): it means the guard
  refused an action — an unprotected modified adapter, or a `rebaseline` that
  needs `--force`. The `0`–`6` map above is `viseinit`'s; `core/manifest.py`
  keeps its own small domain too. Each entry-point family documents its own.

## 3. Adding or changing an adapter

An adapter is the supported way to add a capability. The reference layout is
`adapters/ExampleAdapter_reference/`; copy it and adapt.

Required manifest fields (`vise.adapter.json`):

- `schema_version`, `adapter_id` (unique), `name`, `version`, `description`
- `required_cots` — each entry `"tool"` or `{ "tool", "min_version" }`
- `entry_points` — at least `cli`; add `read` if the adapter exposes
  knowledge content, `extensions` if it ships shell extensions
- `healthcheck` — must actually verify readiness and return non-zero on
  failure (use `$PYTHON`, the `.venv` interpreter, not a bare `python`)
- `commands` — declare every CLI command **with its arguments**, so agents can
  construct calls without `--help` probing

Optional but expected where applicable:

- `provides` (`category` / `tags` / `description`) for resource-library
  categorization (see `visectl list --category` / `--tag`)
- `read` — implement the resource access contract (`visectl read <id> <topic>`)
- `depends_on` — declare adapter dependencies; they are topologically layered
- `python_deps` — third-party packages, aggregated into `.vise/requirements.txt`
  and installed into `.venv` at setup (do **not** list them in `required_cots`)

Checklist for a new adapter:

- [ ] Manifest is complete (fields above) and `commands` match the real CLI.
- [ ] `thread` is idempotent and does not write outside `VISE_ROOT` without
      recording it in the ledger (C9).
- [ ] `healthcheck` genuinely validates readiness.
- [ ] `read` implemented if the adapter exposes knowledge.
- [ ] Adapter `README.md` documents usage, configuration, and the
      absolute-path/cwd caveat where relevant.
- [ ] The adapter passes an **end-to-end self-test** before being proposed:
      `bash init/setup.sh` then `viseinit <adapter_id>` then
      `visectl run <adapter_id> <cmd>` — see [docs/TEST-PLAN.md](docs/TEST-PLAN.md).

### Changing an existing adapter (C13)

An agent that "mostly" solves its task with an existing tool will edit that
tool's source. This path is protected, and it does not assume git — a
zip/tarball install has the same guarantees.

```bash
visectl adapter snapshot <id> -m "why the adapter is about to change"  # open a snapshot
# edit adapters/<Name>/ source (file_patch is the sanctioned writer)
viseinit <id>                                    # validate (init_steps + healthcheck)
visectl adapter restore <id> [--gen N|--base]    # reject: roll back byte-for-byte
visectl adapter promote <id> -m "what changed"   # accept: write .vise/patches/<id>/*.patch
```

- The baseline is captured at install time (`.vise/baseline/<id>/`) and is
  **only written when absent** — re-running `setup.sh` never blesses an edited
  tree as "original". Accepting the current tree as the new reference is
  explicit: `visectl adapter rebaseline <id> [--force]`.
- `promote` writes a reviewable unified diff and **never commits** (C13).
- A modified adapter with no open snapshot is **unprotected**: `visectl run`
  and `promote` refuse it with exit `7`. Use the actions in the message, or
  `visectl run --allow-modified <id> ...` for a deliberate manual customization.
- Snapshots are pruned to the newest 5 generations; an open snapshot is never
  pruned.

## 4. Quality bar

Beyond the contracts, contributions are held to the conventions the project
has already established (see [docs/IMPROVEMENTS.md](docs/IMPROVEMENTS.md) for
worked examples):

- **Declarative over imperative** — express intent in a manifest or config
  file, not in ad-hoc code.
- **Machine-readable by default** — if a human reads it, assume an agent may
  read it too: prefer JSON, typed fields, stable codes.
- **Small and reversible** — delete dead code rather than keeping
  compatibility shims; no speculative abstraction.
- **Explain the "why"** — comments only where the logic is non-obvious;
  commit messages state the reason, not the mechanics.

## 5. Generated artifacts — never commit

If `git status` shows any of these, it is a mistake:

```
.vise/            # tool_paths.json, registry.json, requirements.txt,
                  #   python, state/, reports/, installed.json,
                  #   baseline/, snapshots/, patches/
.venv/            # project virtual environment
__pycache__/      # bytecode
```

They are produced by `bash init/setup.sh` / `viseinit` and are machine-local.
A fresh clone must work after a single `bash init/setup.sh` — never by
committing these files.

## 6. Testing

Every PR must be verified against the test points relevant to its change
surface. The catalog of concrete commands and expected results is in
[docs/TEST-PLAN.md](docs/TEST-PLAN.md). The baseline (T0 + T1, plus the
adapter-guard core of T10) is automated: run `bash tests/smoke.sh` — one
command, also executed by CI. At minimum:

- `bash init/setup.sh` runs clean and is idempotent.
- `viseinit --all` reports every enabled adapter `[OK]` and exits `0`.
- `visectl doctor` reports all adapters OK.
- For any change touching files outside `VISE_ROOT`, run
  `bash init/uninstall.sh --dry-run` and confirm the ledger accounts for them.

Document in the PR which test points you ran and what you saw. "It works on
my machine" is not a test result.

## 7. Pull request process

1. **Open an issue first** for anything that touches a contract in §2, adds an
   adapter, or changes a public interface. Small fixes may go straight to a PR.
2. **Fill in the PR template** — `.github/PULL_REQUEST_TEMPLATE.md`. It is the
   acceptance checklist; maintainers may decline a PR with unchecked items.
3. **Keep PRs focused** — one concern per PR; unrelated refactors belong in a
   separate PR.
4. **Sync the docs.** If you changed a contract, path, command, or manifest
   field, update [README.md](README.md), [AGENTS.md](AGENTS.md),
   [docs/DESIGN.md](docs/DESIGN.md), and the relevant adapter `README.md` in
   the same PR (C12).
5. **Review.** A maintainer verifies the checklist, the test evidence, and
   that no contract in §2 was broken. Approval + green checks are required
   before merge.

Reviewers will reject a PR that: commits generated artifacts; breaks an exit
code or JSON shape; introduces implicit execution; hand-edits the registry;
leaves docs stale after a path/contract change; or ships an adapter that does
not pass its self-test.

---

## 8. Commit conventions

Follow the existing history:

- `feat: ...` — a new capability
- `fix(scope): ...` — a bug fix (`fix(file_patch): ...`)
- `docs: ...` — documentation only
- Message body explains the **why**, not a restatement of the diff.
