# Vise Improvement Proposals

> This document records improvement proposals for the issues identified in [DESIGN.md](DESIGN.md).
> They are ordered by priority, and each item contains: problem description, design proposal, and scope of impact.

---

## P0 Improvements (Implemented)

The following two P0 improvements are in force; see the code for details:

- **P0-1**: each adapter exposes a `thread` bootstrap script as its entry, and the `visectl` unified CLI
  dispatches every adapter; `core/vise_functions.sh` does not loop-source adapter shortcut files,
  so global function name conflicts cannot occur.
- **P0-2**: `core/adapter_paths.json` holds hand-written overrides (nested schema, maintained by developers)
  and `tool_paths.json` holds detected paths (flat schema, generated by the install script);
  each carries a `_doc` field, and the resolver accepts only its own schema.

## P1-1 · init_steps support a structured form

### Problem Recap

The `command` in init_steps was a bare shell string; quote escaping was fragile and no structured arguments were possible.

### Design Proposal

The manifest's `init_steps` supports **two forms**:

**Form 1: structured (recommended)**

```jsonc
"init_steps": [
  {
    "name": "thread bootstrap",
    "run": "bash",              // program
    "args": ["./thread"],       // argument list
    "cwd": ".",
    "timeout_sec": 60
  }
]
```

When `viseinit` executes it, it uses `subprocess.run([run] + args, ...)`, not going through the shell.

**Form 2: shell string (escape hatch, keeps backward compatibility)**

```jsonc
"init_steps": [
  {
    "name": "legacy step",
    "command": "bash ./thread && echo done",
    "timeout_sec": 60
  }
]
```

**Execution logic:** if a `run` field is present → structured execution; otherwise fall back to `command` shell execution.

### Scope of Impact

| Change | File |
| --- | --- |
| `init_adapter()` supports `run`/`args` | `core/viseinit.py` |
| Reference adapter manifest changed to the structured form | per-adapter `vise.adapter.json` |

## P1-2 · required_cots support version checks

### Problem Recap

Dependencies only checked for existence, not version.

### Design Proposal

Each COTS entry in `core/adapter_paths.json` supports `min_version`:

```jsonc
"cots": {
  "python": { "path": null, "min_version": "3.11" },
  "git":    { "path": null, "min_version": "2.40" }
}
```

The manifest's `required_cots` can optionally specify a version:

```jsonc
"required_cots": [
  { "tool": "python", "min_version": "3.11" },
  { "tool": "git" }
]
```

**The resolver adds `resolve_with_version(tool, min_version)`:**
- After resolving the path, run `version_cmd` (default `<tool> --version`)
- Parse the version number and compare whether it is >= `min_version`
- Returns `{"path": "...", "version": "3.13.1", "ok": true}` or `{"path": null, "version": null, "ok": false}`

**Version command mapping table:**

| Tool | version_cmd | Version regex |
| --- | --- | --- |
| python | `--version` | `\d+\.\d+\.\d+` |
| git | `--version` | `git version (\d+\.\d+\.\d+)` |
| 7z | (no standard version output) | skipped |
| code | `--version` | first line |

### Scope of Impact

| Change | File |
| --- | --- |
| `core/adapter_paths.json` adds `min_version` | `core/adapter_paths.json` |
| `vise.adapter.json`'s `required_cots` supports the object format | per-adapter |
| Resolver adds version-check logic | `core/vise_adapter_paths.py` |
| `core/viseinit.py` calls the version check during the dependency-check phase | `core/viseinit.py` |

## P1-3 · Interface enhancements for AI Agents

### Problem Recap

Missing `--json` output, self-discovery capability, and stable error codes.

### Design Proposal

#### New `core/visectl.py` (unified entry CLI)

```
visectl list                           # list all adapters (JSON or table)
visectl describe <id>                  # output manifest content
visectl thread <id>                    # bootstrap a single adapter
visectl thread --all                   # bootstrap all
visectl run <id> <command> [args...]   # run adapter CLI
visectl doctor                         # diagnose only, without running init_steps
```

All commands support a `--json` flag, outputting machine-readable content to stdout.

#### `viseinit --json`

`core/viseinit.py` adds a `--json` flag: it skips the console summary and outputs the full report JSON
to stdout (no file written). AI Agents can parse it directly.

#### Stable error code table

| Exit code | Meaning |
| --- | --- |
| 0 | All passed |
| 1 | Some adapter failed (generic) |
| 2 | Missing dependency |
| 3 | init step failure |
| 4 | healthcheck failure |
| 5 | Unknown adapter id |
| 6 | Manifest format error |

### Scope of Impact

| Change | File |
| --- | --- |
| Add `core/visectl.py` | new file |
| `core/viseinit.py` adds `--json` + finer-grained exit codes | `core/viseinit.py` |
| `core/vise_functions.sh` defines the `visectl` function | `core/vise_functions.sh` |

## P2-1 · Registry changed to be generated by the init script (not a repo-managed file) · Implemented

### Problem Recap

Both `registry.json` and `tool_paths.json` were repo-managed files:
- After adding/removing an adapter, the registry had to be edited by hand, which was easy to forget or get wrong, and with multiple contributors contending for one file, conflicts were easy
- Tool paths differ per machine, so committing them to the repo is meaningless and they go stale

### Design Proposal (Implemented)

The registry is produced by a dedicated generator script:
1. **The registry is generated by a script**: add `init/register_adapters.py`, which scans
   `adapters/*/vise.adapter.json` → generates `registry.json`
   (`adapter_id` uniqueness check, warn-and-skip invalid manifests, and
   `"enabled": false` in a manifest can disable an adapter)
2. **COTS paths refreshed by environment detection**: `setup.sh` re-detects
   the local machine's tools on every run and overwrites `tool_paths.json` (idempotent refresh)
3. **Neither is repo-managed**: both files are added to `.gitignore`; after a fresh clone,
   running `bash init/setup.sh` once generates them
4. **Clear prompt when missing**: when the registry is missing, `viseinit` / `visectl` prompts
   "Run: bash init/setup.sh" and exits with code 1

An adapter's single source of truth = the `adapters/` directory + each adapter's `vise.adapter.json`,
and the registry is merely its machine-local projection. Because every machine generates its own
registry after a fresh clone, there is no shared registry file for multiple contributors to contend over.

### Scope of Impact

| Change | File |
| --- | --- |
| Add registry generator | `init/register_adapters.py` (new file) |
| setup adds a generation step + idempotent refresh | `init/setup.sh` |
| Ignore generated artifacts | `.gitignore` |
| Prompt for missing registry | `core/viseinit.py`, `core/visectl.py` |

## P2-2 · Parallel execution + `--keep-going` / `--fail-fast` + dependency topology · Implemented

### Problem Recap

Serial execution was slow, and failure semantics were coarse. If adapters depend on each other
(A needs B initialized first), naive parallelism would cause adapters whose dependencies were not
ready to fail.

### Design Proposal (Implemented)

**Parallelism + failure semantics**:
- `viseinit --jobs N` (default 1): run N adapters in parallel (`ThreadPoolExecutor`)
- `viseinit --keep-going` (default): continue with subsequent work after some adapter fails
- `viseinit --fail-fast`: abort immediately after the first failure, marking the remaining adapters as `skipped`
- `--keep-going` and `--fail-fast` are mutually exclusive (`add_mutually_exclusive_group`)
- console summary adds a `[SKIP]` marker, and the JSON report summary adds a `skipped` field

**Adapter dependencies (`depends_on`)**:
- A manifest may declare `"depends_on": ["other_adapter_id"]` (optional field)
- `dependency_layers()` uses Kahn's topological sort to split adapters into multiple layers:
  - Layer 0 = adapters with no dependencies → can run in parallel
  - Layer N = adapters depending on Layer 0..N-1 → parallel after the previous layers complete
- Layers run serially (Layer N+1 waits for all of Layer N to finish), and within a layer it parallelizes according to `--jobs`
- Circular dependency detection: adapters that cannot be layered are marked as `skipped`; non-circular adapters run normally
- `--fail-fast` applies across layers: a failure in one layer → all subsequent layers are skipped

### Scope of Impact

| Change | File |
| --- | --- |
| Add `dependency_layers()` topological layering (Kahn's algorithm) | `core/viseinit.py` |
| Add `_run_layer()` single-layer parallel execution | `core/viseinit.py` |
| Rewrite `run_adapters()` layered scheduling | `core/viseinit.py` |
| Add `--jobs` / `--keep-going` / `--fail-fast` arguments | `core/viseinit.py` |
| console summary adds a `[SKIP]` marker + jobs/fail-fast mode display | `core/viseinit.py` |
| JSON report `summary` adds a `skipped` field | `core/viseinit.py` |
| manifest schema adds optional `depends_on` field | adapter manifests |

## P2-3 · State/report lifecycle management · Implemented

### Problem Recap

Reports grew unbounded, and state had no invalidation.

### Design Proposal (Implemented)

- `visectl clean --reports`: clean up report files older than 30 days (keeping `latest.json`)
- `visectl clean --state`: clean up the `.vise/state/` directories of adapters no longer present in the registry
- `visectl clean` (no flag): do both by default
- `visectl clean --dry-run`: only show what would be deleted, without actually deleting
- `visectl clean --json`: machine-readable output (removed/kept lists)
- The report threshold is controlled by the `REPORT_TTL_DAYS = 30` constant

### Scope of Impact

| Change | File |
| --- | --- |
| Add `cmd_clean()` + the `clean` subcommand | `core/visectl.py` |
| Add `REPORTS_DIR` / `STATE_DIR` / `REPORT_TTL_DAYS` constants | `core/visectl.py` |

## P3-1 · Resource library abstraction (manifest adds a `provides` field) · Implemented

### Problem Recap

The 8-grid resource vision existed only as a document description and was not queryable architecturally.

### Design Proposal (Implemented)

The manifest adds an optional `provides` field:

```jsonc
{
  "provides": {
    "category": "tools",     // tools | work_instruction | database | ai_chat | plan | todo | onedrive | external
    "tags": ["example", "reference"],
    "description": "Reference adapter showing the Vise adapter contract."
  }
}
```

- `visectl list --category tools`: filter by category
- `visectl list --tag reference`: filter by tag
- `visectl list --json`: the output includes the `provides` field (if present)
- `visectl describe <id>`: the human-readable output shows a `provides` block
- `provides` is entirely optional — adapters without this field are not filtered but are listed normally

### Scope of Impact

| Change | File |
| --- | --- |
| manifest adds a `provides` field example | `adapters/ExampleAdapter_reference/vise.adapter.json` |
| `cmd_list` supports `--category` / `--tag` filtering | `core/visectl.py` |
| `cmd_describe` displays `provides` information | `core/visectl.py` |
| `list --json` output includes `provides` | `core/visectl.py` |

## IA-1 · Install flow improvements: multi-shell detection + uninstall script · Implemented

### Problem Recap

1. `setup.sh` only wrote `~/.bashrc` — zsh users (the default on some Linux distributions) would not get it loaded
2. There was no uninstall script — the Vise block in `~/.bashrc` could not be cleanly removed, and generated artifacts could not be cleaned in one command

### Design Proposal (Implemented)

**Multi-shell detection**:
- `setup.sh` step 4 adds `detect_rc()`: detects `$SHELL`, bash→`~/.bashrc`, zsh→`~/.zshrc`, others fall back to `~/.bashrc`
- The post-install hint uses the actual rc file name (`source ~/.zshrc` instead of a hardcoded `~/.bashrc`)
- Only bash and zsh are supported (target platforms: Linux terminal + Git Bash, both bash; zsh may appear on Linux)

**uninstall script** (`init/uninstall.sh`):

```bash
bash init/uninstall.sh             # remove shell block + all artifacts
bash init/uninstall.sh --keep      # remove only the shell block, keep artifacts
bash init/uninstall.sh --dry-run   # preview without deleting
```

| Cleanup item | Default | `--keep` |
| --- | --- | --- |
| The Vise block in `~/.bashrc` / `~/.zshrc` | ✅ | ✅ |
| `.vise/` (tool paths, registry, requirements, state, reports) | ✅ | ❌ |
| `.venv/` | ✅ | ❌ |

- The rc block is removed with Python `re.sub` (avoiding `sed -i` temporary-file permission issues)
- Both bashrc and zshrc are checked (the shell may have been switched)
- Markers are matched exactly (`# >>> Vise >>>` / `# <<< Vise <<<`), so other content is not accidentally removed

### Scope of Impact

| Change | File |
| --- | --- |
| `detect_rc()` + improved output hints | `init/setup.sh` |
| Add uninstall script | `init/uninstall.sh` (new file) |
